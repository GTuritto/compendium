**Note on the sources count.** The smoke playbook expects `one new row in sources`, but the live walk ingested a file whose content hash already exists in the dev DB (the same byte content as `tests/fixtures/sample.pdf`, ingested in prior smoke walks). The pipeline returns `status="unchanged"`, which the inbox treats as success per resolved decision #4. The file is correctly routed to `processed/<today>/` and the summary reports it as processed — the contract holds. The "new sources row" expectation in the smoke wording is too strict on a populated dev DB; a follow-up will relax the wording to `>=` pre-count (or note the unchanged-success path explicitly).

## v0.2-4.3 — Drop a unique-content corrupt PDF

```sh
echo "NOT-A-PDF-$(date +%s%N)" > /tmp/cdb-inbox-smoke/paper/garbage-<timestamp>.pdf
uv run python -m compendium inbox process --path /tmp/cdb-inbox-smoke
```

| Check | Result |
| --- | --- |
| Result | PASS |
| Exit | 0 |
| Routed to `failed/2026-05-31/` | ✓ `garbage-1780209065961721000.pdf` |
| Sidecar `.error` written | ✓ `garbage-1780209065961721000.pdf.error` |
| Sidecar content | `could not open PDF: Failed to open file '...'.` |

**Concurrent-fire observation.** Because v0.2-4.1 left the LaunchAgent loaded, the launchd watcher fired the moment the corrupt file landed in `paper/`. By the time the manual `inbox process` invocation reached the file, the launchd-fired worker had already routed it. The manual fire reports `processed=0 failed=0 skipped=0` and emits a `"inbox race lost"` structlog event — a clean demonstration of the atomic-rename race semantics (resolved decision: no advisory locks; lose the race on `FileNotFoundError`). End state matches the contract: file + sidecar both present in `failed/<today>/`.

## Findings

1. **v0.2-4.2's "one new sources row" expectation is too strict on a populated dev DB.** A re-dropped good file with an already-known content hash returns `status="unchanged"` and routes to `processed/<today>/` per resolved decision #4 — the contract holds, but the dev-DB-naive wording reads as a failure. Worth a follow-up to relax the smoke wording to "`sources` row count does not decrease" or to explicitly note the `unchanged → processed` path.

2. **The launchd watcher fires the moment a file lands.** v0.2-4.3 demonstrated this by accident: the auto-fire from launchd raced with the manual `inbox process`, and the atomic-rename + `FileNotFoundError` lost-race handling kept everything clean. This is the contract working as designed — not a finding to fix.

3. **Status remains usable after uninstall.** v0.2-4.6 confirmed the resolved-decision #2 behaviour: `compendium inbox status` reports `watcher_loaded=False` but still returns the full filesystem-derived snapshot and exits 0. The inbox is usable manually even when the watcher is uninstalled.
