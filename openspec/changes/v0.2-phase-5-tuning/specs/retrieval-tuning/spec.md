## ADDED Requirements

### Requirement: The golden runner computes per-query `coverage_score`, `recall@K`, and `MRR`

For each query in `tests/golden/dataset.yaml`, the golden runner SHALL compute three metrics:

- `coverage_score`: the normalized top-page coverage already recorded on `query_traces.coverage_score`.
- `recall@K`: 1.0 when the expectation's `must_include_slug` appears within the first `K` final-ranking entries, else 0.0. `K` SHALL be the `retrieval.top_k` value from `config/settings.yaml` (default 7). When the expectation has no `must_include_slug`, `recall@K` is `null`.
- `MRR`: 1.0 divided by the 1-indexed rank of the first `must_include_slug` hit in the final ranking, or 0.0 when the slug is not in the top-`K`. When the expectation has no `must_include_slug`, `MRR` is `null`.

The runner SHALL also emit per-category and overall aggregates over the queries where each metric is defined.

#### Scenario: Per-query metrics computed for a Category A query

- **GIVEN** a Category A query whose `must_include_slug` appears at rank 2 of the final ranking
- **WHEN** the golden runner computes metrics
- **THEN** the entry includes `coverage_score` (the trace value), `recall@K=1.0`, and `MRR=0.5`

#### Scenario: Category C query has `null` for recall@K and MRR

- **GIVEN** a Category C query whose expectation only carries `fallback_to_chunks=true` and no `must_include_slug`
- **WHEN** the golden runner computes metrics
- **THEN** `recall@K` and `MRR` are `null`; `coverage_score` is populated

### Requirement: `tests/golden/baseline.json` carries the captured numbers and is regenerated on demand

The repository SHALL include `tests/golden/baseline.json` carrying the per-query and aggregated metrics. The file SHALL be regenerated by running `uv run pytest -m golden --golden-baseline`; without that flag, the golden runner SHALL load `baseline.json` and compare live metrics against it. A live run that regresses any metric by more than `0.01` absolute (per query OR in aggregates) SHALL fail the golden assertion.

#### Scenario: Default golden run compares to baseline and passes within tolerance

- **WHEN** `uv run pytest -m golden` runs against the same code as captured the baseline
- **THEN** the per-query metrics match the baseline within `0.01` absolute; the suite passes

#### Scenario: A regression triggers a test failure

- **GIVEN** a code change that drops the `coverage_score` aggregate by `0.05`
- **WHEN** `uv run pytest -m golden` runs against the baseline
- **THEN** the suite fails with a clear message naming the regressed metric and the delta

#### Scenario: `--golden-baseline` regenerates the file

- **WHEN** `uv run pytest -m golden --golden-baseline` runs
- **THEN** `tests/golden/baseline.json` is overwritten with the live metrics; the suite passes (no comparison)

### Requirement: Rule-based query normalization in `pipeline.query`

The system SHALL apply rule-based normalization to the query text at the head of `compendium.retrieve.pipeline.query()`, before BM25 + dense fan-out. The normalization SHALL: (a) lowercase the input; (b) strip a curated set of English stop-words; (c) expand any matched alias (from `wiki_pages.aliases` where `kind='concept'`) to its canonical title. The order SHALL be lowercase → stop-words → alias expansion. The normalized query SHALL drive the fan-out; the trace SHALL persist both the raw text (`query_text`) and the normalized form (`normalized_query` field).

#### Scenario: Stop-words and case are normalized

- **WHEN** `compendium query "The Psychological Safety concept"` runs
- **THEN** the fan-out queries are issued against the text `"psychological safety concept"`

#### Scenario: Alias expansion canonicalizes the query

- **GIVEN** the concept page `psychological safety` carries the alias `"psych safety"`
- **WHEN** `compendium query "psych safety"` runs
- **THEN** the fan-out queries are issued against `"psychological safety"`

#### Scenario: No-match queries pass through

- **WHEN** `compendium query "an unrelated phrase"` runs
- **THEN** the fan-out query is `"unrelated phrase"` (lowercased, stop-words stripped, no alias expansion)

### Requirement: `AliasIndex` is cached per-process and refreshable

The system SHALL provide an `AliasIndex` class with class methods `from_db(conn)`, `refresh()`, and `expand(text) -> str`. A module-level cache SHALL hold one instance per process; `query()` uses the cached instance. The cache SHALL be invalidated by an explicit `refresh()` call.

#### Scenario: First query loads the index lazily

- **GIVEN** a fresh Python process
- **WHEN** `compendium.retrieve.pipeline.query()` is called for the first time
- **THEN** one `SELECT` against `wiki_pages` runs to populate `AliasIndex`

#### Scenario: Subsequent queries reuse the cached index

- **WHEN** `compendium.retrieve.pipeline.query()` is called again in the same process
- **THEN** no additional `SELECT` runs against `wiki_pages` (the cached `AliasIndex` is reused)

### Requirement: OpenSearch analyzer uses English Snowball + a synonym filter

The OpenSearch index mappings for `pages.body` and `chunks.body` SHALL use a custom analyzer named `compendium_english` consisting of: standard tokenizer; lowercase filter; English Snowball stemmer filter; synonym filter sourced from a generated `synonyms.txt`. The `title` fields SHALL retain a lighter `standard` analyzer to preserve exact-match recall on titles. The synonyms file SHALL be regenerated on every `compendium reindex pages` and `compendium reindex all` from `wiki_pages.aliases` in `alias_a, alias_b => canonical_title` (one-directional) form.

#### Scenario: An alias query matches a document via the synonym filter

- **GIVEN** a page with title `psychological safety` and alias `psych safety`; `synonyms.txt` carries `psych safety => psychological safety`; the index has been rebuilt
- **WHEN** an OpenSearch query for `psych safety` runs
- **THEN** the page is returned in the hits (the analyzer expanded the alias to the canonical token)

#### Scenario: An English-stemmed query matches a stemmed document

- **GIVEN** a page whose body contains "experimenting"
- **WHEN** an OpenSearch query for `experiment` runs against the body field
- **THEN** the page is returned (the Snowball stemmer reduces both to `experi`)

### Requirement: Qdrant HNSW parameters are configured deliberately

Qdrant collection creation SHALL pass an `hnsw_config` with explicit `m` and `ef_construct` values; search calls SHALL pass `hnsw_ef` via `SearchParams`. The values SHALL be chosen by the tuning loop in 5c and committed to `compendium/index/qdrant.py` as constants. The starting point is `m=16, ef_construct=128, hnsw_ef=64`; the loop may revise.

#### Scenario: The Qdrant collection carries the chosen HNSW config

- **WHEN** the curator runs `compendium reindex all`
- **THEN** the `pages` and `chunks` Qdrant collections are created with the documented `m` and `ef_construct` values

#### Scenario: Searches pass the chosen `hnsw_ef`

- **WHEN** `compendium.retrieve.pipeline.query()` issues a Qdrant search
- **THEN** the `SearchParams` payload carries the documented `hnsw_ef`

### Requirement: Tuning iterations improve at least two of the three metrics

After applying the Phase 5 analyzer and HNSW changes and re-running the golden suite, the new aggregates in `tests/golden/baseline.json` SHALL show improvement on at least two of `coverage_score`, `recall@K`, and `MRR` against the v0.1-default baseline (captured before the analyzer + HNSW changes). No golden assertion SHALL regress (the Phase 10 regression-detector contract).

#### Scenario: Post-tuning aggregates improve

- **GIVEN** the v0.1-default baseline aggregates {coverage_A: x1, recall_A: y1, mrr_A: z1, ...}
- **WHEN** the Phase 5 analyzer + HNSW changes are applied and `--golden-baseline` regenerates the baseline
- **THEN** at least two of the post-tuning aggregates exceed the corresponding pre-tuning values; no golden assertion fails

### Requirement: Operational document and smoke section

The repository SHALL include `docs/operations/retrieval-tuning.md` covering: the three metric definitions; reading `baseline.json`; the `--golden-baseline` regeneration flag; the tuning loop (change → reindex → regenerate → compare → accept-or-revert); the synonyms pipeline (`wiki_pages.aliases` → `synonyms.txt` → OpenSearch); the stop-words list and rationale; suggested next steps when a metric flatlines. `tests/manual/smoke_test.md` SHALL include a Phase 5 (v0.2) section covering: baseline regeneration, default golden run comparing to baseline, query normalization end-to-end, OpenSearch analyzer applied, Qdrant HNSW applied, tuning iteration meets the ≥2-of-3 gate.

#### Scenario: The operational doc covers the required sections

- **WHEN** the curator reads `docs/operations/retrieval-tuning.md` after Phase 5 merges
- **THEN** the document explains the metric definitions, baseline regeneration, the tuning loop, the synonyms pipeline, stop-words, and flatline next steps

#### Scenario: The smoke walk exercises the tuning loop end-to-end

- **WHEN** the operator walks the Phase 5 (v0.2) smoke section
- **THEN** they regenerate the baseline, run the default golden suite, drop an alias and re-query, reindex with the new analyzer, and observe the ≥2-of-3 improvement
