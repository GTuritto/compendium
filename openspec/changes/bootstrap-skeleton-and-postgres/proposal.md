## Why

Compendium is fully designed (a 127KB reference doc with vision, 9 ADRs, data contracts, and a 10-phase build plan) but nothing is built — there is no Python project, no config, no database. The build plan cannot start, and no later phase can be tested, until a runnable project skeleton and the operational system of record exist. This change delivers Phase 0 and Phase 1: a project that starts and validates its configuration, plus the full PostgreSQL schema that every subsequent phase reads from and writes to.

## What Changes

- New `uv`-managed Python 3.12 project: `pyproject.toml`, `.python-version`, dependency set.
- Package layout: `compendium/{ingest,wiki,index,retrieve,graph,trace,tui,db}/`, plus `config/`, `migrations/`, `tests/`, `vault/`.
- Configuration system: `.env.example` (secret/URL vars), `config/settings.yaml` (non-secret behavior config), and a loader that resolves env-var references at startup and validates them.
- `python -m compendium` entrypoint that loads and validates config, prints "Compendium starting" and the resolved storage URLs, and exits cleanly. Config validation is parse/resolve only — no connection attempts.
- Structured logging: `structlog` emitting JSON to stderr.
- A dev-only single-service `docker-compose.yml` running a pinned `postgres:16`.
- Alembic initialized against `POSTGRES_URL`, configured for hand-written (non-autogenerated) sync migrations.
- The full operational PostgreSQL schema as hand-written Alembic migrations in the documented 10-step order: enums; `sources`/`source_documents`; `corpus_revisions`; `chunks`; `wiki_pages`/`wiki_pages_topics`; `wiki_page_revisions` (with the deferred circular `current_revision_id` FK); `index_sync_state`; `promotion_events`; `query_traces`; `graph_curation_signals`/`graph_analysis_runs`; and the four read-only TUI views.
- A thin `compendium/db/` repository module wrapping `psycopg 3` (sync) for connection management and queries — no ORM.
- Deviation from the design doc, deliberately scoped here: `query_traces.query_embedding` is `REAL[]` rather than `VECTOR(1024)`; pgvector is **not** installed in v0.1 (sanctioned by the doc's stated fallback — vector search lives in Qdrant, not Postgres).
- `README.md` with setup instructions and the doc reading order.

## Capabilities

### New Capabilities

- `project-skeleton`: A runnable, configured Python project — package layout, dependency management, the `python -m compendium` entrypoint, configuration loading and validation, and structured logging.
- `operational-database`: The PostgreSQL operational system of record — the full table/enum/view schema, expressed as ordered Alembic migrations that apply and reverse cleanly, plus a sync `psycopg 3` access layer.

## Impact

- New project: `pyproject.toml`, `uv.lock`, `.python-version`, `.env.example`, `.gitignore`, `README.md`, `docker-compose.yml`.
- New code: `compendium/` package (with sub-packages, most empty placeholders for later phases), `config/settings.yaml` + loader, `migrations/` (Alembic env + versioned migrations), `tests/` (config + schema smoke tests).
- New dependencies: `psycopg[binary]` (v3), `alembic`, `structlog`, `pyyaml`, `python-dotenv`, plus `pytest` for tests.
- New external runtime dependency: a running PostgreSQL 16 (provided by the dev `docker-compose.yml`).
- Repository initialized with `git init` (the project is not yet a git repo).
- Sets foundational technical decisions inherited by all later phases: sync DB access, raw SQL over an ORM, native Postgres enums, and pgvector deferred.
