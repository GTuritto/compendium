# v0.2 Phase 3 — Scheduled curation daemon: Implementation Plan

Date: 2026-05-30
Branch: `v0.2-phase-3-daemon` (off `main`)
OpenSpec change: `openspec/changes/v0.2-phase-3-daemon/`
Spec source: [docs/COMPENDIUM_V0.2_BUILD.md](../docs/COMPENDIUM_V0.2_BUILD.md) § Phase 3;
[docs/Compendium.md](../docs/Compendium.md) ADR-012 (always-on personal
service — this phase ships it).

## Goal

Make Compendium a personal always-on service: the slow loop runs on a
schedule under launchd / systemd; an installer / uninstaller writes
and removes the unit.

## Why this plan exists

v0.1 ships the curation slow loop as an on-demand `compendium curate
run` CLI invocation. In practice that means signals only accumulate
when the curator remembers — exactly when there is least time to
react. ADR-012's posture wants the slow loop firing on a schedule, so
"thin grounding" and "low coverage" signals are ready to drain when
the curator sits down.

Phase 3 ships the smallest mechanism that satisfies that: a per-OS
user-level scheduler unit (launchd LaunchAgent on macOS, systemd user
timer on Linux) that fires `compendium curate run` on a configured
cadence. The unit is installed by `compendium schedule install
[--every 1h]` and removed by `compendium schedule uninstall`;
`compendium schedule status` reports loaded-state and last/next
firings. The unit survives a host reboot.

The plan locks five decisions:

1. **Timer-fires-CLI is the v0.2 interim.** ADR-012's "alternatives
   considered" section rejected this approach in favour of the access
   surface's daemon hosting the schedule. The rejection is
   conditioned on the access-surface daemon existing, which it does
   not until Phase 7. Phase 3 ships the timer-fires-CLI now; Phase 7
   (or a later refactor) absorbs the schedule into the daemon.
2. **`compendium schedule install` over `compendium curate install`.**
   The build plan's acceptance is literal: `compendium schedule
   install [--every 1h]`. Future scheduled targets (Phase 4 inbox,
   future v0.3 work) plug into the same dispatcher rather than
   proliferating top-level verbs.
3. **Cadence parser accepts `Nh` / `Nm` / `NhMm`** (human-readable);
   minimum granularity 60 s; maximum 7 d. Default `1h` when `--every`
   omitted.
4. **User-level units only.** No system-wide (root) units; no
   sub-minute cadences; no in-process daemon. v0.2 Phase 3 is
   deliberately the smallest reversal of "no daemon" that satisfies
   ADR-012's posture.
5. **Phase 2 backup installer keeps its own code path in v0.2.**
   Refactoring `compendium backup install` to use the new generic
   scheduler is a v0.3 candidate, not a Phase 3 deliverable.

## Sub-phases

### 3a — `compendium schedule install` / `uninstall`

**Purpose:** ship the install + uninstall half — generate the OS-native
unit, register it with the scheduler, remove it idempotently.

**Tasks:**

1. `compendium/schedule/__init__.py`: re-exports
   `install_schedule`, `uninstall_schedule`, `ScheduleError`,
   `ScheduleResult`.
2. `compendium/schedule/cadence.py`:
   `parse_interval(value: str) -> int` accepting `Nh`, `Nm`, `NhMm`;
   returns total seconds; raises `ScheduleError` on `<60s`, `>604800s`,
   or malformed input.
3. `compendium/schedule/install.py`: platform detect (darwin / linux);
   macOS branch writes `~/Library/LaunchAgents/com.compendium.curate.plist`
   with `StartInterval=<seconds>` and `ProgramArguments` invoking
   `uv run --project <repo> python -m compendium curate run`; Linux
   branch writes `~/.config/systemd/user/compendium-curate.{service,
   timer}` with `OnUnitActiveSec=<seconds>` and `Persistent=true`;
   macOS loads via `launchctl bootstrap gui/<uid>`; Linux enables via
   `systemctl --user enable --now`.
4. `compendium schedule install [--every <interval>]` CLI verb.
   Defaults `--every` to `1h`. Prints the resolved unit path + loader
   exit code.
5. `compendium schedule uninstall` CLI verb. Unloads then removes the
   unit; idempotent (no error when nothing is installed).
6. Unit tests for cadence parsing (valid / invalid), plist XML
   contains correct `StartInterval`, systemd timer unit contains
   correct `OnUnitActiveSec`, non-darwin/linux `sys.platform` is
   refused with a clean message.

**Files added:** `compendium/schedule/__init__.py`,
`compendium/schedule/cadence.py`, `compendium/schedule/install.py`
**Files modified:** `compendium/__main__.py` (`schedule` subparser +
`_schedule` handler)

**Decision flagged:** the install code path duplicates a handful of
helpers from `compendium/backup/schedule.py` (label conventions,
LaunchAgent skeleton, systemd unit skeleton). Factoring out is a v0.3
refactor; Phase 3 keeps the duplication.

### 3b — `compendium schedule status`

**Purpose:** the curator runs one command and sees whether the unit
is loaded and when it last / next fires.

**Tasks:**

1. `compendium/schedule/status.py`: `read_status() -> ScheduleStatus`
   with fields `loaded: bool`, `last_fired: datetime | None`,
   `next_fire: datetime | None`, `unit_path: Path`.
2. macOS: runs `launchctl print gui/<uid>/com.compendium.curate`,
   parses the output for `state`, `last exit`, `next launch`. Missing
   fields → `None`.
3. Linux: runs `systemctl --user list-timers --all
   compendium-curate.timer` and `systemctl --user status
   compendium-curate.service`; parses for `LAST`, `NEXT`, `Active`.
   Missing fields → `None`.
4. `compendium schedule status` CLI verb. Exits 0 when loaded; exits
   1 when not installed. Supports `--format text` (default) and
   `--format json`.
5. Unit tests with stubbed `subprocess.run` outputs: loaded unit,
   never-fired unit, not-installed unit.

**Files added:** `compendium/schedule/status.py`
**Files modified:** `compendium/__main__.py`,
`compendium/cli/render.py` (small render helper for the status text)

**Decision flagged:** `launchctl print` and `systemctl status` text
formats are stable but not contractual. The parser tolerates missing
fields rather than asserting exact field shapes; future macOS / systemd
releases that change the output do not break the command — just yield
"unknown" values until the parser is updated.

## Out of scope for Phase 3 (do NOT build)

- A long-running compendium daemon process. Phase 7's access-surface
  daemon is the long-term home; Phase 3 is the timer-fires-CLI
  interim.
- System-level (root) scheduler units. User-level only.
- Sub-minute cadences.
- Cadence reconfiguration without uninstall / reinstall.
- Refactoring `compendium backup install` to use the new generic
  scheduler (v0.3 candidate).
- Hosting any other CLI verb in the scheduler. v0.2 Phase 3 hosts
  only `compendium curate run`. Phase 4 (inbox) and later phases may
  add targets.
- TUI integration for schedule status. CLI surface only in v0.2.
- Email or push notifications when a fire fails. Operators read the
  OS scheduler logs.
- Sidecar state files mirroring the scheduler. The OS scheduler is
  the source of truth.

## Open questions to confirm before starting

1. **Default cadence.** `--every 1h` matches the existing
   `loops.slow_loop_interval_seconds: 3600` in
   `config/settings.yaml`. Recommendation: keep `1h`.
2. **CLI verb naming.** `compendium schedule install` (per build
   plan) vs `compendium curate install` (parallel to Phase 2
   backup). Recommendation: `compendium schedule install` — single
   dispatcher for future scheduled targets.
3. **Cadence configuration source.** Install-time `--every` only,
   no `settings.yaml` override. Recommendation: confirmed.
4. **Integration test approach.** Manual kick via OS scheduler (no
   waiting) rather than natural cadence (slow + brittle).
   Recommendation: confirmed.
5. **Refactor `compendium backup install`?** Defer to v0.3.
   Recommendation: confirmed.
