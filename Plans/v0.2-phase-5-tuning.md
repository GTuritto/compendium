## Goal

Improved retrieval quality on the golden set, measured; rule-based
query normalization in the `query` hot path (Shape D part 1).

## Why this plan exists

v0.1 froze the retrieval substrate at library defaults: OpenSearch's
default English analyzer, Qdrant HNSW at qdrant-client defaults,
and a raw query string passed straight into the BM25 + dense
fan-out. Phase 10 proved this is consistent across runs but never
measured how *good* the retrieval is. v0.2's thesis is "better
answers"; Phase 5 is where the substrate gets sharpened.

Three concrete deliverables:

1. **A measurable baseline.** Per-query `coverage_score`,
   `recall@K`, and `MRR` extend the golden runner; the captured
   numbers live in `tests/golden/baseline.json`. From this commit
   onward every retrieval change is evaluated against a fixed file,
   not the curator's memory.
2. **Rule-based query normalization** in `pipeline.query()` —
   lowercase, English stop-words, alias expansion against
   `wiki_pages.aliases`. Zero LLM cost on the hot path. LLM-based
   rewriting is absorbed into Phase 6's `ask` (Shape D part 2).
3. **Tuning iterations** on the OpenSearch analyzer (English
   Snowball stemmer + synonym filter sourced from page aliases) and
   the Qdrant HNSW parameters (`m`, `ef_construct`, `hnsw_ef`). The
   gate: at least two of the three metrics improve against the
   baseline; no golden assertion regresses (Phase 10's regression
   detector is the contract).

The plan locks five decisions:

1. **Baseline regeneration is a pytest flag**
   (`uv run pytest -m golden --golden-baseline`), not a new CLI
   verb. The golden harness lives inside pytest; a CLI wrapper
   would duplicate setup code.
2. **Tolerance is `0.01` absolute.** Allows small stochastic RRF
   tie-breaks; keeps the gate meaningful.
3. **Synonyms are one-directional** (`alias_a, alias_b =>
   canonical_title`). The canonical token always wins; tighter
   precision than bidirectional.
4. **Stop-words first, then alias expansion** in the normalizer.
   Drop `the` etc. before checking for an alias match.
5. **HNSW starting point: `m=16, ef_construct=128, hnsw_ef=64`.**
   More aggressive than qdrant-client defaults; the tuning loop in
   5c may revise.

## Sub-phases

### 5a — Baseline metrics + golden runner extension

**Purpose:** measure the v0.1-default retrieval quality and freeze
it as the comparison baseline.

**Tasks:**

1. `tests/golden/__init__.py`:
   `compute_metrics(trace, expectation) -> dict` returning
   `{coverage_score, recall_at_k, mrr}` per query.
2. `K` reads from `retrieval.top_k` in `config/settings.yaml`
   (default 7).
3. `summarize(per_query) -> dict` aggregates per-category and
   overall means; ignores `null` entries from queries that lack a
   `must_include_slug`.
4. `tests/test_golden.py`: register `--golden-baseline` pytest CLI
   flag via a conftest fixture (or `pytest_addoption`). When set,
   the runner writes the live numbers to `tests/golden/baseline.json`
   and skips the comparison assertion.
5. `tests/golden/baseline.json`: capture current numbers under the
   v0.1-default analyzer + HNSW defaults. Committed as a fresh
   file.
6. `tests/test_golden.py`: a new test loads `baseline.json`, runs
   the golden suite, and asserts no metric regresses by more than
   `0.01` absolute against the corresponding baseline entry.

**Files added:** `tests/golden/baseline.json`
**Files modified:** `tests/golden/__init__.py`,
`tests/test_golden.py` (or a new `tests/conftest.py` for the flag)

**Decision flagged:** the baseline is committed to the repo. PRs
that intentionally change ranking quality must regenerate the
baseline and explain the delta in the PR body.

### 5b — Rule-based query normalization

**Purpose:** strip the query of noise and resolve aliases before
the fan-out hits the indexes.

**Tasks:**

1. `compendium/retrieve/normalize.py`:
   - `class AliasIndex` with `from_db(conn)`, `refresh()`,
     `expand(text) -> str`.
   - Module-level cache; one instance per process.
2. `normalize_query(text, alias_index) -> str`: lowercase → strip
   stop-words → alias expansion. The curated stop-word list is a
   small set (~15 words) defined in the module.
3. `compendium/retrieve/pipeline.py`: at the head of `query()`,
   call `normalize_query()` on the input; thread both the raw and
   normalized text into the trace payload (raw on
   `query_traces.query_text`; normalized via the existing trace
   metadata channel or a small dedicated field).
4. The cached `AliasIndex` instance is created lazily on first
   `query()` invocation and reused across calls in the same
   process.
5. Unit tests for `normalize_query`: lowercase; stop-words;
   alias expansion; no-match passthrough.
6. Unit tests for `AliasIndex`: lazy load; `from_db()` reads
   correctly; `refresh()` re-reads.

**Files added:** `compendium/retrieve/normalize.py`
**Files modified:** `compendium/retrieve/pipeline.py`,
`tests/test_retrieval.py` (new test cases)

**Decision flagged:** Phase 7's `serve` daemon will need a
refresh hook for `AliasIndex` (the daemon is long-running; aliases
change as the corpus grows). Phase 5 ships the cache + manual
refresh; the hook is a Phase 7+ concern.

### 5c — OpenSearch analyzer + Qdrant HNSW tuning iterations

**Purpose:** sharpen the indexes themselves and pick the parameter
set that improves ≥2 of 3 metrics against the baseline.

**Tasks:**

1. `compendium/index/synonyms.py`:
   `generate_synonyms_file(conn, output_path: Path)` reads
   `wiki_pages` aliases and writes
   `<alias_a>, <alias_b> => <canonical_title>` one entry per
   concept (skipping concepts with no aliases).
2. `compendium/index/opensearch.py`: replace the default analyzer
   on `body` fields with a custom `compendium_english` analyzer
   (standard tokenizer + lowercase + `english_snowball` filter +
   `synonyms` filter pointing at the generated file). `title`
   fields keep the lighter `standard` analyzer.
3. `compendium/index/qdrant.py`: collection-create passes
   `HnswConfigDiff(m=16, ef_construct=128)`; search-call passes
   `SearchParams(hnsw_ef=64)`.
4. Reindex helper calls `generate_synonyms_file()` before
   re-creating the OpenSearch index so the new analyzer reads the
   current alias set.
5. **Tuning loop** (operator-driven, not automated). Starting with
   the v0.1-default baseline captured in 5a:
   - Apply the analyzer + HNSW changes from 5c.1–5c.3.
   - Run `compendium reindex all`.
   - Run `uv run pytest -m golden --golden-baseline` to regenerate
     the baseline.
   - Compare the new aggregates to the prior baseline (kept as
     `tests/golden/baseline.v01-default.json` for the duration of
     the tuning).
   - If `>=2` aggregates improved AND no golden assertion failed,
     accept the new baseline. Otherwise revert and try a different
     parameter set.
   - Commit the chosen `m / ef_construct / ef` as constants in
     `compendium/index/qdrant.py`.
6. Unit-level: verify the synonyms file generator emits the
   expected format and skips concepts with no aliases.

**Files added:** `compendium/index/synonyms.py`
**Files modified:** `compendium/index/opensearch.py`,
`compendium/index/qdrant.py`,
`compendium/index/sync.py` (or wherever the reindex helper lives),
`tests/test_indexes.py` (new test cases for analyzer + HNSW config)

**Decision flagged:** the v0.1-default baseline file
(`baseline.v01-default.json`) is kept in the branch during the
tuning loop for comparison and is removed before merge — only the
final post-Phase-5 `baseline.json` lands on `main`.

## Out of scope for Phase 5 (do NOT build)

- LLM-based query rewriting (Phase 6's `ask`).
- A separate live-tier golden with real embeddings.
- Edge n-grams in the OpenSearch analyzer.
- Per-query analyzer overrides.
- Learning-to-rank, ranker training, or non-RRF fusion.
- A TUI screen for the tuning loop.
- A new top-level CLI verb for the tuning loop.
- Auto-updating synonyms via `synonym_graph` with `updateable=true`
  (defer to v0.3 if alias churn becomes a problem).
