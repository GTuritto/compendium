Date: 2026-05-30
Branch: `v0.2-phase-2-backup` (off `main`)
OpenSpec change: `openspec/changes/v0.2-phase-2-backup/`
Spec source: [docs/COMPENDIUM_V0.2_BUILD.md](../docs/COMPENDIUM_V0.2_BUILD.md) § Phase 2;
[docs/Compendium.md](../docs/Compendium.md) ADR-001 (vault canonical), ADR-004 (Postgres
system of record).

## Goal

Postgres + vault snapshots, restorable, with an off-host destination.

## Why this plan exists

v0.1 ships no backup or restore path. The two authoritative stores
(PostgreSQL by ADR-004, the vault by ADR-001) live on a single
laptop. An accidental `docker compose down -v`, an `rm -rf vault/`
typo, or a dead SSD costs the curator every ingested source, every
synthesized page, every revision, every trace. v0.2 Phase 2 ships the
smallest mechanism that lets the operator trust the system enough to
ingest real personal material:

1. A scriptable `compendium backup` that pairs a `pg_dump
   --format=custom` of the database with a `tar.gz` of the vault,
   timestamped, written to a configurable local directory.
2. An optional `rsync` to `BACKUP_RSYNC_DEST` so a single-device
   failure does not lose the corpus.
3. A scriptable `compendium restore <timestamp>` that drops both
   stores back into place and prints the derived-store rebuild
   reminder.
4. A daily-by-default scheduled unit (launchd on macOS, systemd user
   timer on Linux) installed by `compendium backup install`.

The plan locks four decisions:

1. **Only the system of record is backed up.** Derived stores
   (OpenSearch, Qdrant, Memgraph) rebuild deterministically from
   PostgreSQL and the vault; backing them up would only add restore
   complexity. The operational doc states this explicitly.
2. **Full snapshots, not incremental.** Vault is small; database is
   small; `pg_dump --format=custom` + `tar.gz` is enough. No WAL
   archiving, no `pg_basebackup`.
3. **Schedule installer is Phase-2-specific.** Phase 3's generic
   `compendium schedule install` can absorb the backup unit later;
   v0.2 Phase 2 ships its own thin installer so "daily by default"
   is actually achievable in one command on a fresh host.
4. **`--force` for destructive restore over a non-empty vault.** The
   single-user posture makes this the right guard level; the
   operational doc names the rationale.

## Sub-phases

### 2a — `compendium backup` CLI (pg_dump + tar + optional rsync)

**Purpose:** the local backup half — emit a timestamped pair, mirror
to off-host if configured. No restore logic in this commit.

**Tasks:**

1. `compendium/config.py`: add `backup_local_dir: str` and
   `backup_rsync_dest: str` to `Config`; populate from
   `config/settings.yaml`'s new `backup:` section.
2. `config/settings.yaml`: new `backup:` block sourcing
   `${BACKUP_LOCAL_DIR:-./backups}` and `${BACKUP_RSYNC_DEST:-}`.
3. `.env.example`: add `BACKUP_LOCAL_DIR=./backups` and
   `BACKUP_RSYNC_DEST=` with comment block.
4. `.gitignore`: add `backups/`.
5. `compendium/backup/__init__.py` + `compendium/backup/backup.py`:
   `run_backup(config, *, timestamp=None) -> Path`. Verifies
   `pg_dump` and `tar` are on `PATH`; creates
   `<local_dir>/<UTC-timestamp>/`; runs `pg_dump --format=custom -f
   compendium.dump <POSTGRES_URL>`; runs `tar -czf vault.tar.gz -C
   <vault parent> <vault leaf>`; when `BACKUP_RSYNC_DEST` is set,
   runs `rsync -a --info=stats2 <local>/<ts>/ <dest>/<ts>/`; cleans
   up the partial directory on any failure; emits structlog events
   per step.
6. Wire `compendium backup` CLI verb (no positional args); exit 0 on
   success, non-zero on failure with a structured error.
7. Unit-level tests in `tests/test_backup.py` for the helpers that
   are mockable (timestamp shape, missing-binary check); the
   round-trip integration test lands in 2d.

**Files added:** `compendium/backup/__init__.py`,
`compendium/backup/backup.py`
**Files modified:** `compendium/config.py`, `config/settings.yaml`,
`.env.example`, `.gitignore`, `compendium/cli.py` (or the verb router)

**Decision flagged:** the rsync step is fire-and-forget per backup;
no destination verification. Operators with stricter expectations can
add their own post-hook script — out of scope here.

### 2b — `compendium restore <timestamp>` CLI

**Purpose:** the symmetric restore half. Drops + restores the
database via `pg_restore --clean --if-exists`; replaces the vault;
prints the derived-store rebuild reminder.

**Tasks:**

1. `compendium/backup/restore.py`:
   `run_restore(config, timestamp, *, force) -> None`. Validates
   `<local_dir>/<timestamp>/{compendium.dump,vault.tar.gz}` exist;
   checks `pg_restore` and `tar` on `PATH`.
2. Non-empty-vault guard: when any `*.md` exists under `VAULT_PATH`
   and `force=False`, exit 1 with
   `vault is not empty; pass --force to overwrite`. No database
   operation is performed.
3. Database restore: `pg_restore --clean --if-exists --no-owner
   --dbname=<POSTGRES_URL> compendium.dump`. Non-zero exit names the
   failing step.
4. Vault restore: remove `*.md` recursively under `VAULT_PATH`;
   extract `vault.tar.gz` into the vault parent; verify the
   extracted layout includes `concepts/`, `topics/`, `sources/`.
5. Print to stdout (not just structlog):
   `Run 'compendium reindex all' and 'compendium graph rebuild' to
   repopulate the derived stores.`
6. Wire `compendium restore <timestamp> [--force]` CLI verb.

**Files added:** `compendium/backup/restore.py`
**Files modified:** `compendium/cli.py`

**Decision flagged:** `pg_restore --clean --if-exists` is the safe
operation against a possibly-empty database; the v0.1 fixture data
and any Phase 1 walk artifacts will be wiped during the smoke walk —
documented in the operational doc.

### 2c — Schedule install / uninstall (launchd + systemd user)

**Purpose:** the daily-by-default deliverable from the Phase 2
acceptance. One command on a fresh host installs the scheduled
backup; one removes it.

**Tasks:**

1. `compendium/backup/schedule.py`: platform detection via
   `sys.platform`; one code path for `darwin` (LaunchAgent plist),
   one for `linux` (systemd user service + timer). Refuses
   non-supported platforms with a clean message.
2. macOS branch: write
   `~/Library/LaunchAgents/com.compendium.backup.plist`;
   `ProgramArguments` invokes
   `["/usr/bin/env", "uv", "run", "--project", <repo>, "python", "-m",
   "compendium", "backup"]`; `StartCalendarInterval` carries
   `Hour`/`Minute` (default 02 / 00, overridable via `--at HH:MM`);
   `StandardOutPath` + `StandardErrorPath` under
   `~/Library/Logs/compendium/`; load with `launchctl bootstrap
   gui/<uid> <plist>`.
3. Linux branch: write
   `~/.config/systemd/user/compendium-backup.service` and
   `compendium-backup.timer`; the service's `ExecStart` invokes the
   same uv-driven command; the timer's `OnCalendar=*-*-* HH:MM:00`
   per `--at`; enable with
   `systemctl --user enable --now compendium-backup.timer`.
4. `compendium backup install [--at HH:MM]` CLI verb. Validates
   `HH:MM` shape; refuses cadences finer than one minute. Prints the
   resolved unit path and the loader command's exit code.
5. `compendium backup uninstall` CLI verb. Unloads then removes the
   unit; idempotent (no error when nothing is installed).
6. Optional `compendium backup status` that prints
   `launchctl print` (macOS) / `systemctl --user status` (Linux) — a
   thin one-liner so the operator can confirm the unit is loaded.

**Files added:** `compendium/backup/schedule.py`
**Files modified:** `compendium/cli.py`

**Decision flagged:** the LaunchAgent + systemd user timer paths run
as the curator's user — no system-level units, no root. macOS users
may need to grant "Full Disk Access" to Terminal/uv if the vault
path is under a protected directory; documented in the operational
doc.

## Out of scope for Phase 2 (do NOT build)

- Backup encryption (operator uses SSH-tunnelled rsync or an
  encrypted destination filesystem).
- Incremental backups via `pg_basebackup` / WAL archiving — full
  snapshots only.
- Restore directly from the rsync destination (operator brings the
  file back manually; a future phase can add
  `restore --from-remote` if it earns its place).
- Automatic retention / pruning of old local backups.
- Multi-destination fanout.
- Backup of the derived stores (OpenSearch / Qdrant / Memgraph).
- TUI integration (a backup screen) — out of scope; the CLI is the
  surface in v0.2.
- A `compendium backup status` JSON output for monitoring — the
  thin status command in 2c is operator-facing only.

## Open questions — resolved at the review gate (2026-05-30)

1. **Backup directory default.** RESOLVED: option (a) — `./backups/`
   (in-repo, gitignored, discoverable). Override path documented in
   `docs/operations/backup-restore.md`.
2. **Schedule installer scope in Phase 2.** RESOLVED: option (a) —
   ship `compendium backup install` / `uninstall` now as a
   Phase-2-specific scheduler. Phase 3's generic
   `compendium schedule install` can refactor / absorb the backup
   unit later without breaking this phase's acceptance.
3. **Vault tarball compression.** RESOLVED: gzip (`tar -czf`).
   Universal, adequate at this corpus size.
4. **`--force` semantics on restore.** RESOLVED: `--force` is
   required when the live vault contains one or more `.md` files;
   `pg_restore --clean --if-exists` runs unconditionally (an empty
   database is the right default).
5. **Default cadence.** RESOLVED: 02:00 local time, daily, with
   `--at HH:MM` override at install time. Configurable cadence
   (`--every 12h`) deferred until someone asks.
