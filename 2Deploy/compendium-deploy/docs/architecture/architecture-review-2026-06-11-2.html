Problem

Three byte-identical client constructions and five copies of the chat-completion envelope; token accounting exists in one path out of three.

Solution

One chat(system, user, *, on_token=None) → Completion module beside the model-client registry; the three classes shrink to prompt builders and parsers.

  • locality: envelope and usage rules live once
  • leverage: one interface, five call sites
  • synth + extract gain token accounting free
  • streaming variant exercised in one place
  • deletion test: copies reappear 5×

The reasoning

What's there now

The line self._client = OpenAI(base_url=endpoint, api_key=api_key or "not-needed") appears verbatim at answer/llm.py:90, wiki/synth.py:59, and curate/extract.py:183 (re-verified this evening — untouched by today's merges). Around it, the same mechanical envelope — chat.completions.create(model=…, messages=[system, user]) then choices[0].message.content or "" — repeats five times: rewrite (llm.py:94-108), buffered compose (llm.py:121-131), streaming compose (llm.py:133-154), synthesize (synth.py:62-79), label (extract.py:186-198). The Completion dataclass and the usage-or-_approx_tokens fallback (llm.py:25-36) exist only in the answerer; the synthesizer and extractor discard response.usage — and the new profile stats verb now makes that asymmetry visible: its ask section prices token counts the synth and extract paths never record.

What changes

One deep function — roughly chat(role_cfg, system, user, *, on_token=None) → Completion — owns client construction, the create call, the streaming loop with include_usage, and the usage fallback. Completion moves to that shared home. Everything role-specific stays put: the Answerer/Synthesizer/Extractor protocols, the stub classes, the prompts, _parse_labels, and the get_model_client registry (PR #54), which keeps owning stub-or-real selection — this candidate adds the mechanical call behind that seam, it does not reopen it.

Why

The deletion test passes cleanly: delete the helper and the envelope reappears at five call sites in three modules. Locality: retry/error/usage conventions, when they evolve, change in one place. Leverage: the streaming path — the trickiest copy — is tested once and reused; the extractor and synthesizer get token accounting without writing it, which feeds straight into profile stats. The hermetic tier is untouched because the stubs never cross this seam.

Problem

The seam exposes probe() exactly for status readers, with an injectable Runner — and zero readers use it; two re-implement platform dispatch and the scheduler-CLI calls.

Solution

Both readers consume Probe; their field-extraction regexes stay. On Linux the seam grows the richer probe the readers actually need.

  • deletes duplicated platform dispatch ×2
  • status readers testable via fake Runner
  • locality: scheduler CLI quirks live once
  • deletion test: probing reappears per reader
  • finishes PR #48's documented intent

The reasoning

What's there now

service_unit.probe() (service_unit/__init__.py:86-94) returns a Probe whose docstring reads "the raw scheduler-CLI output the service parses for interval / next-fire / host:port" (errors.py:37-48) — and it takes an injectable Runner so tests never touch a real launchctl. Its only caller outside the package is inbox/install.py:105. Meanwhile schedule/status.py dispatches on sys.platform itself (line 50) and runs launchctl print gui/<uid>/… directly (lines 85-86) — the identical command launchd.probe runs at launchd.py:137 — and api/service.py does the same dance again (platform dispatch at 162-164, launchctl at 139, systemctl is-active at 152-153). All anchors re-verified this evening. Today's CI work sharpened the cost: the unit-kick test had to be skipped under CI precisely because this layer is hard to fake — with the Runner injected at the seam, the status readers' parsing becomes testable against recorded CLI output everywhere, including runners.

What changes

Both readers call service_unit.probe(descriptor) and parse Probe.stdout. Their rich field extraction — the interval/next-fire regexes, _parse_host_port — stays in each service, exactly as the seam's docstring assigns it. The one real design point: on Linux, systemd.probe runs is-enabled, but the schedule reader needs status + list-timers output — so the seam grows a second probe shape (or a probe verb parameter) rather than readers owning subprocess. On macOS it is a drop-in.

Why

This is finishing an existing seam, not adding one — three adapters (schedule, serve, inbox) make it unambiguously real. The interface is the test surface: with the Runner injected at the seam, status readers become pure parsers over recorded CLI output, which is precisely the part worth regression-testing. Locality: when launchctl output shifts across macOS releases, the fix lands in one adapter, not two readers. The deletion test on the bypassed code passes today in reverse: the duplicated probing can be deleted with no complexity reappearing, because the seam already holds it.

3 · Name the index-document shape once

Worth exploring in-process carried forward

index/documents.py · index/opensearch.py · retrieve/search.py · retrieve/pipeline.py

Before — one implicit shape, four restatements

documents.py builders

"title" "slug" "status"
"body" / "body_preview"

opensearch.py mappings

"title" "slug" "status"
"body" …

search.py field lists

["title^2","aliases","body"]

pipeline.py consumers

f.get("title", "")
f.get("body") or f.get("body_preview")

a renamed field silently returns "" — no test fails

After — one named shape, three derivations

PageDoc / ChunkDoc
the field contract, typed once
to OpenSearch doc
ISO ts
to Qdrant payload
unix-ms, preview
typed hit reader
pipeline consumes

Problem

The page/chunk document shape exists only as matching string keys across writer, mappings, search field lists, and .get() consumers — an untyped seam with silent-default failure.

Solution

Declare the shape once in documents.py (typed record or field constants); derive both store dicts and the hit readers from it. Wire format stays byte-identical.

  • field drift fails at construction, not silently
  • locality: shape evolution touches one module
  • per-store body/body_preview split stops leaking
  • deletion test: shape reappears in 4 files

The reasoning

What's there now

The page shape is written four times: page_document/page_payload restate eleven shared keys (documents.py:42-82); the OpenSearch mappings restate the names with analyzer config (opensearch.py:60-77); search restates the searchable subset (_PAGE_FIELDS, search.py:28-29); and the pipeline reads it all back through Hit.fields: dict[str, Any] (search.py:38) with silent defaults — f.get("title", "") (pipeline.py:97). The per-store difference leaks past the seam: _chunk_citation must know OpenSearch carries body while Qdrant carries body_preview (pipeline.py:108, re-verified). Rename a field in one of the four and retrieval degrades to empty strings; nothing fails until the golden tier notices rankings drift.

What changes

One declaration of the shape in documents.py — a frozen record per entity kind is the obvious form, with to_opensearch()/to_qdrant_payload() adapters owning the ISO-vs-unix-ms and body-vs-preview differences, and a typed reader for hits coming back. The wire JSON, the mappings' analyzer config, the StoreProjector registry (PR #25), and RRF fusion all stay put; the exact form (records vs a constants module) is a grilling-loop decision because re-hydrating store responses has a small cost the hot path should choose deliberately.

Why

Today the interface between projection and retrieval is invisible — it lives in string literals four files apart, so the test surface doesn't exist: nothing can assert "writer and reader agree" except an end-to-end query. The deletion test passes: drop the named shape and the contract re-disperses into all four sites. Locality: v0.2 Phase 5 already grew this shape once (aliases for synonyms); the next retrieval-tuning phase will again. This remains the highest AI-navigability win on the list: "what fields does a page hit carry?" becomes one definition.

Problem

The facade promises the transports cannot drift, yet the ingest decision tree is duplicated in both, and page_get's not-found behaviour has already drifted (HTTP 404 vs MCP null).

Solution

The facade absorbs base64 decoding, the path-or-bytes validation, and a single documented not-found convention; transports keep only transport-native concerns.

  • error modes become part of one interface
  • facade tests cover both transports' semantics
  • deletes the duplicated decision tree
  • deletion test: tree reappears per transport

The reasoning

What's there now

The facade's own docstring states the contract: "The MCP and HTTP transports are thin shells over this module; neither holds business logic, so the two surfaces cannot drift" (facade.py:6-8). Mostly true — most verbs are one-liners. But the ingest input logic (decode content_base64, choose path-vs-bytes, reject neither) is written twice, at http.py:69-94 and mcp.py:73-94 (anchors re-verified after today's serve-signal change shifted http.py), with separately-maintained error text. And drift is not hypothetical: on a missing page, HTTP raises 404 (http.py:101) while MCP returns JSON null (mcp.py:97-98). Error modes are part of the interface, and right now each transport defines its own. Today's ci-smoke.sh had to assert the ingest contract over HTTP separately from the CLI for exactly this reason.

What changes

facade.ingest grows to accept the surface's actual input shape (content_base64 + filename alongside path) and owns decoding and the either/or validation with one error message; the facade documents one not-found convention for page_get that both transports express natively (404 / null are fine as renderings of one decision, made once). What stays put: the six-verb set (ADR-011), to_payload serialization, the chunked-HTTP and MCP-notification streaming bridges — those are genuinely transport-native.

Why

The facade is the access surface's interface, and the interface is the test surface: today "rejects ingest with neither path nor bytes" must be tested per transport or goes untested. After the move, one facade test covers both callers — leverage. The deletion test passes: inline the coercion and it reappears in two transports (three when a future transport lands — ADR-011 defers MCP-SSE and LAN HTTP to v0.3, so the third adapter is already on the roadmap). No tension with ADR-011; this enforces the no-drift promise it already makes.

Assessed this pass — benign or mandated, recorded so future reviews stop

The new surface from PRs #63–#68 was swept with fresh eyes; all three findings below fail the case for a seam. The morning pass's rejections (off-queue graph rebuild, per-entity query DSL, reachability dedup, import-time profiling flag) all still stand.

Timed-span stage names as free strings — leave as is. Ten stage literals across four modules, restated in the docs table. The stats SQL aggregates whatever keys exist, so nothing breaks on rename; an enum would be a pass-through wrapper with no leverage (every call site still names its own span). The convention is documented; the deletion test fails.
CI service-container blocks copied four times — mandated duplication. GitHub Actions strips YAML anchors, composite actions cannot declare job-level services, and reusable workflows cannot parameterize them. ~27 lines × 4 jobs is the only portable form. Not a code smell; a platform constraint.
CLI dispatch if-chain (21 branches, 1070-line `__main__.py`) — healthy, no verb registry. Every branch is a single tail call into a parse → call → render handler; a registry would wrap the chain without shrinking any call site (argparse construction cannot be data-driven away). Revisit only if branches double or handlers grow logic.
The ten profile-stats repository readers — deliberately thin. Plain SELECTs behind the ADR-004 raw-SQL rule; the same mandated shallowness recorded for the rest of repository.py in review #1.
