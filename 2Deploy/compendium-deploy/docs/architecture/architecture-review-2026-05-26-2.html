Architecture review #2 — Compendium

2026-05-26 · second pass
Since review #1: candidate 1 (the CLI presentation seam, compendium/cli/render.py) is implemented in PR #20. This pass re-confirms the still-open candidates and explores the modules #1 didn't touch — the TUI, the synth/promote/curation path, and the ingest/wiki write path.

The headline finding: shipping the CLI render seam exposed its mirror image. The six TUI screens re-implement the same scalar formatting the render seam just centralized — coverage to three places, the same date format, the fallback flag. Presentation now leaks across two surfaces. The rest are deepenings of workflows whose ordering lives in callers rather than in one module.

One home for `fmt_coverage`, `fmt_ts`, `fmt_fallback`; CLI strings and TUI cells both consume them.

Problem
The render seam centralized CLI formatting, but the TUI screens still reformat the same scalars in their _populate methods — coverage, timestamps, the fallback flag, payload truncation. Change a format and you touch render plus up to six screens.

Solution
Extract the scalar formatters (fmt_coverage, fmt_ts, fmt_fallback) into the render module; the TUI builds its table cells from them. CLI gets whole-string renderers, TUI gets the per-cell pieces — both from one place.

Wins

  • locality: one format, both surfaces
  • leverage: the render seam already exists — extend it
  • deletion test: format reappears in 6 screens
  • tests already cover the formatters (test_render)

Problem
The entity→store mapping is re-derived across documents.py, projection.py, and a separate rebuild.py; Memgraph isn't on index_sync_state, so it has no per-row failure recovery. The smoke walk made this concrete: `graph rebuild` after promote wiped the auto-added `SYNTHESIZES` edge, because rebuild re-derives only the structural edges.

Solution
One projection interface, one adapter per store; the graph joins the sync queue so all three drain and recover through one path.

Wins

  • locality: schema change hits one module
  • graph gains per-row recovery
  • three adapters make the seam real
  • one drain path to test
ADR note: consistent with ADR-005 (stores stay derived); revisits only the implicit off-queue rebuild choice.

3 · The curation lifecycle as one deep operation

curate/synth.py · trace/promote.py · curate/promote_hook.py · __main__.py · tui/screens/curation.py

Before · ordering lives in callers

caller: synth_from_signal() → draft, signal in_progress
↓ caller must remember to promote
promote() → re-writes vault, snapshot
↓ inline import
address_on_promote() → close signal, add edges (silent no-op if not found)

The invariant "open → in_progress → addressed" lives in no single module. Synth-but-never-promote leaves a signal stuck forever; no type or seam prevents it.

After · one module owns the transition

curate lifecycle module

owns the open → in_progress → addressed state machine and the promote+address ordering; callers express intent, not sequence.

CLI and TUI both call one entry; the hook stops being an inline import buried in promote().

Problem
Synth → promote → address spans four modules; the ordering and the signal state machine live in callers (an inline import inside promote(), a silent no-op in the hook). Nothing prevents out-of-order or half-finished transitions.

Solution
One module owns the signal lifecycle and the promote+address ordering; the hook becomes part of that module's implementation, not a caller responsibility.

Wins

  • locality: the state machine in one place
  • leverage: CLI + TUI share one entry
  • stuck-signal class of bug disappears
  • interface is the test surface
ADR note: keep curator approval (ADR-009: no autonomous promotion). This deepens the locality of the workflow — it does not auto-promote; the curator still triggers the transition.

4 · Collapse the TUI load cycle into one Screen helper

tui/screens/*.py (10 repetitions) · tui/data.py

The same five lines, ten times

@work(thread=True, exclusive=True)
def load(self):
    try:
        payload = tui_data.dashboard()
    except Exception as exc:
        self.app.call_from_thread(self._error, str(exc))
        return
    self.app.call_from_thread(self._populate, payload)

This block recurs across all six screens (10 worker actions). The "run blocking call in a thread → route result or error back to the UI" cycle is pure boilerplate.

A Screen base method — self.load_async(fn, on_ok=self._populate) — would absorb the decorator, the try/except, and the two call_from_thread hops.

Problem
@work(thread=True) + try/except + two call_from_thread calls is copied into ten screen actions; the thread-safety contract is restated each time.

Solution
One Screen base helper owns the load-or-error cycle; screens pass a data function and a populate callback.

Wins

  • locality: thread-safety contract in one place
  • leverage: every screen action shrinks to one call
  • deletion test: the cycle reappears 10×
  • error routing becomes consistent
