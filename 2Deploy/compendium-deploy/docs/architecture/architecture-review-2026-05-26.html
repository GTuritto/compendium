Architecture review — Compendium

2026-05-26 · v0.1 (phases 0–10 merged)

The deep seams already exist and are exemplary — the Embedder protocol with its stub/real adapters, pipeline.run()'s injectable clients, the graph-expansion hook that never leaks Memgraph into retrieval. The friction concentrates in four places where modules stayed shallow: presentation re-derived per call site, the projection mapping copied per store, store-client construction duplicated across a sync/async split, and a repository whose shallowness is mandated by an ADR.

Modules own their aggregates; one render seam, two adapters (text, json).

Problem
Aggregation, a raw SELECT, client construction, and ~17 one-off formatters leak into the CLI; the modules hand back bare lists and dicts.

Solution
Modules return rich result objects; one presentation module renders any of them as text or JSON. Handlers shrink to parse → call → print.

Wins

  • interface shrinks at every handler
  • locality: formatting in one module
  • leverage: formatters become pure, testable
  • deletes the raw SQL from the CLI
  • two adapters justify the seam: text, json
  • deletion test: complexity reappears across 17 sites

All three drain — and recover — through one path; the mapping lives once.

Problem
The entity→store mapping is re-derived across documents.py, projection.py, a three-branch _write_one, and a separate rebuild.py; Memgraph isn't on index_sync_state, so it has no per-row failure recovery.

Solution
One "project entity to derived stores" interface with one adapter per store; the graph joins the sync queue so all three drain and recover through one path.

Wins

  • locality: schema change hits one module
  • leverage: one drain path for all stores
  • graph gains per-row failure recovery
  • three adapters make the seam real
  • "how a page reaches all indexes" reads in one place
  • tests target the projection interface, not 6 files
ADR note: consistent with ADR-005 (the stores stay derived and distinct). It revisits only the implicit choice that graph rebuild is an off-queue command — worth reopening because that asymmetry is a real recovery gap, not a styling preference.

3 · One factory + lifecycle per store, mirroring db.connection

index/clients.py · retrieve/clients.py · graph/client.py · db/connection.py

Before

db/connection.py

Postgres: one managed seam — connection() commits/rolls back/closes.

index/clients.py + retrieve/clients.py

OpenSearch/Qdrant: URL-from-config + ctor args copied across sync and async factories.

graph/client.py

Memgraph: driver built in 6 modules, .close() by hand — no enforced lifecycle.

After

shared resolution + lifecycle

One config→URL resolver; a graph_connection() context manager like Postgres'.

Sync (indexing) and async (query) stay as two real adapters — they share resolution, not return type.

Memgraph closure becomes structural, not a thing 6 call sites must remember.

Problem
OpenSearch/Qdrant URL+arg construction is duplicated across the sync and async factories; Memgraph drivers are built in six modules and closed by hand, unlike the one enforced Postgres lifecycle.

Solution
A single config-resolution step plus a graph_connection() context manager mirroring db.connection. The sync/async split stays — it's two genuine adapters.

Wins

  • locality: URL/auth logic in one place
  • leverage: enforced close, like Postgres
  • two adapters (sync index, async query) are real
  • removes a class of leaked-driver bugs

4 · repository.py boilerplate (mostly leave it shallow)

compendium/db/repository.py · 1035 lines · 53 functions

Shallow by design — interface surface ≈ implementation

iface

impl

~75% are one-query pass-throughs: interface nearly matches implementation.

iface

impl

The deep ones already earn their keep: enqueue_index, set_page_topics, ensure_corpus_revision.

Problem
Three identical all_*_ids functions, duplicated dynamic WHERE-builders, and inconsistent UUID coercion (str vs UUID at the seam).

Solution
Collapse only the trivial duplication and standardize UUID coercion. Do not add a query-builder or ORM.

ADR note — don't deepen broadly: the repository's shallowness is mandated by the "raw SQL, no ORM; thin db/ repository" rule. A deeper query abstraction would contradict it. Listed so future reviews stop re-suggesting it — the only real win here is deleting copy-paste, not adding depth.

Tackle first

1 · Pull presentation out of the CLI

Highest leverage for the lowest risk: it touches no ADR, concentrates the most scattered complexity (~17 formatters, an inline query, client wiring), and turns presentation into pure, testable adapters behind one seam. Do it first, then candidate 2 — the projection seam — for the deeper architectural payoff of giving Memgraph the same per-row recovery the other two stores already have.
