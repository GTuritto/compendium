# v0.5 Proposal (parked) — Agent object store + promote path

**Status:** Proposed, **deferred**. This is a parked design, not an active phase. It is gated behind the v0.4 verdict and must not be implemented until the core bet has been measured. See the unlock condition in §1.

**Origin:** Requested 2026-06-14 — "Compendium should not be only a memory for agents; it has to also be a context provider and storage for agents." Scoped through three decisions (recorded in §2). Captured as a design so it is ready the moment v0.4 returns a verdict, without jumping the v0.4 queue.

**ADR:** carries a draft **ADR-017** (§4). The draft lives here, not in the canonical ADR list in [Compendium.md](../Compendium.md), because it is not accepted. On acceptance it is promoted into Compendium.md and this file is archived.

---

## 1. Why this is parked (the v0.4 gate)

The active build, [COMPENDIUM_V0.4_BUILD.md](../COMPENDIUM_V0.4_BUILD.md), exists to answer one question: does a maintained wiki of curated pages actually out-retrieve raw chunks on a real corpus, with corpus size held constant. Its exclusions section defers exactly this proposal, by name and on purpose:

> **Agent-memory writers (Ubongo, AgentTrader as callers).** Deferred to v0.5 or later. The undrawn line between agents ingesting and agents synthesizing or linking stays undrawn until the thesis has a verdict. Building shared memory on top of an unproven engine spends the entire deferred bundle to serve an engine you might rework or kill.

> **The deferred bundle: exposure, auth, namespacing, TLS, MCP-SSE, gRPC, pgvector.** Earned together, by the agent-memory case, which is itself deferred.

The promote path (§3.3) is precisely the "undrawn line between agents ingesting and synthesizing." So this design is held until the gate opens.

**Unlock condition.** v0.4 Phase 1 (the single-point A/B, ADR-016) returns a result that the page-first engine is worth building on — a page-arm advantage over the chunk-only control arm on the real probe set, not an artifact of corpus growth. If the bet fails, this proposal is reworked or dropped along with the engine it sits on. If it holds, this becomes the first v0.5 phase.

**No queue-jump.** Nothing here is built, branched for implementation, or wired into a surface now. This file is docs-only.

## 2. Scope (resolved decisions)

Three questions fixed the scope on 2026-06-14:

1. **What "storage" holds — both a raw store and a promote path.** A verbatim agent-owned object store, plus a one-way bridge to push a chosen object through synthesis into the canonical wiki. Not wiki-only (no verbatim read-back), not raw-only (that would be a second system of record with no on-ramp to the curated knowledge).
2. **Namespacing — ignored for now; one agent.** Single namespace, no per-agent isolation, no auth beyond the existing loopback/LAN posture (ADR-011). A `collection` column is kept as a cheap forward hook but no multi-tenancy is built. The deferred bundle (auth, real namespacing, exposure) stays deferred.
3. **Context provision — enough as is.** The existing `query` / `ask` / `page_get` / `page_list` verbs already serve context to colocated agents. No new context-delivery verb (no task-scoped bundles, no push/subscribe) in this proposal.

Net effect: memory and context provision are unchanged; the new capability is an agent-owned scratch-and-artifact layer with a clean, curator-respecting on-ramp into the wiki.

## 3. Design

### 3.1 The store

A new operational table, `agent_objects`, in PostgreSQL. PostgreSQL because it is already the system of record (ADR-004) and because stack discipline forbids a separate object store. The table sits beside `sources` and `query_traces` as operational data; it is **not** the wiki and **not** a derived index.

| Column | Type | Notes |
|---|---|---|
| `id` | UUID PK | Stable identity. |
| `collection` | TEXT | Default `'default'`. Forward hook for namespacing; not access-controlled in v0.5. |
| `key` | TEXT | Agent-chosen identifier. Unique per `(collection, key)`. |
| `content_type` | TEXT | E.g. `text/markdown`, `application/json`, `text/plain`. Drives interpretation on read. |
| `body` | BYTEA | Verbatim payload, returned byte-for-byte. (Text is the common case; binary supported via content_type. Size guidance, not a hard cap, in the open questions.) |
| `metadata` | JSONB | Agent-supplied tags. |
| `created_at` / `updated_at` | timestamptz | Upsert by `(collection, key)`, last write wins. |

Migration `0015_agent_objects` (next free number after `0014_contradiction_candidate`).

The store is never synced into OpenSearch, Qdrant, or Memgraph. Until an object is promoted (§3.3), it is invisible to retrieval.

### 3.2 Access-surface verbs

Five new verbs on the shared facade ([compendium/api/facade.py](../../compendium/api/facade.py)), exposed on **both** REST and MCP, reusing the existing serializer so the wire JSON stays byte-for-byte identical to `--format json` and cannot drift:

- `object_put(key, value, content_type?, collection?, metadata?)` — store or overwrite; returns the stored record.
- `object_get(key, collection?)` — verbatim value + metadata, or not-found.
- `object_list(collection?, prefix?)` — keys + metadata (bodies optional; see open questions).
- `object_delete(key, collection?)`.
- `object_promote(key, collection?, kind='note')` — the bridge in §3.3.

Matching CLI verbs (`compendium object put|get|list|rm|promote`) for inspection and debugging, consistent with the repo rule that every capability has a CLI. Curator/ops verbs stay CLI-only as before.

### 3.3 The promote path

`object_promote` runs the object's body through the existing ingest pipeline as a source of the given `kind`, then syncs the indexes. The object becomes a source document, gets a deterministic `source` page (ADR-001 permits auto-generated source pages), gets chunked and indexed, and is from then on queryable like any other source. The resulting source records its origin object id as provenance, so the lineage is traceable.

Promote is **one-way** and **stops at the source layer**: it never autonomously creates `concept` pages or semantic edges. Concept synthesis and linking remain curator-driven (and, for `RELATED_TO`/`PREREQUISITE_FOR`, the existing autonomous extractor under the curator's confidence gate). This is the line the v0.4 plan wanted left undrawn; promote draws it conservatively — agents can ingest, but they cannot synthesize.

### 3.4 What it preserves

- **ADR-001 (wiki canonical):** the raw store is not the wiki and is not indexed until promoted, so the canonical knowledge layer is unchanged.
- **ADR-003 (page-first retrieval):** `query` and `ask` keep returning only synthesized pages; un-promoted objects never appear in retrieval.
- **ADR-004 (PostgreSQL is SoR):** the store is a PostgreSQL table, not a new store, not a new system of record competing with the wiki.
- **Synthesis is curator-driven:** promote creates sources only, never concepts.
- **ADR-011 posture:** single-namespace, no auth, loopback/LAN. The deferred bundle stays deferred.

## 4. Draft ADR-017: Agent object store with a one-way promote path (v0.5)

**Status:** Proposed (parked, v0.5). Gated behind the v0.4 verdict (ADR-016). Not accepted; not implemented.

### Context

Compendium is a memory and context provider for a colocated agent (it ingests, synthesizes, and serves cited pages over MCP + HTTP). It has no place for an agent to store an artifact or working-state blob and read it back verbatim: `ingest` transforms its input through synthesis, and the wiki is curated, deduplicated, and citable by design. The agent needs durable, verbatim, agent-owned storage, with an on-ramp into the curated knowledge for the items worth keeping — without turning Compendium into a second, unsynthesized system of record or reopening the deferred multi-tenancy bundle.

### Decision

Add `agent_objects`, a PostgreSQL-backed key-value store (verbatim body, content type, metadata, upsert by `(collection, key)`, last write wins), exposed on the existing access-surface facade as `object_put` / `object_get` / `object_list` / `object_delete` / `object_promote` over REST and MCP, plus mirrored CLI verbs. The store is never indexed into the derived stores. `object_promote` runs an object through the existing ingest pipeline to become a `source` page (indexed, queryable, provenance-linked back to the object); it never creates concept pages or semantic edges. Single namespace, no auth (loopback/LAN, per ADR-011); a `collection` column is reserved but uncontrolled.

### Consequences

- The agent gains real read-back storage and a curator-respecting on-ramp to the wiki, while `query`/`ask` and every existing surface are provably unchanged (the Phase 0 wire-format snapshots plus new per-verb snapshots hold).
- PostgreSQL stays the single system of record; the store is operational data, deletable as a unit (drop `validate/`-style: remove the verbs and the table and no other code depends on them).
- Promote is one-way and source-only, so "synthesis is curator-driven" survives. Agents can ingest; they cannot synthesize.
- The deferred bundle (auth, namespacing, exposure, TLS) is not earned or built here; this is single-agent storage on a loopback/LAN surface.

### Alternatives considered

- **Raw store only (no promote).** Rejected: a second store with no path into the curated knowledge is a parallel system of record, the thing ADR-001/004 exist to prevent.
- **Wiki only (extend `ingest`, no verbatim store).** Rejected: synthesis transforms content, so there is no byte-for-byte read-back, which is the core of "storage for agents."
- **A separate object store (S3/MinIO/etc.).** Rejected by stack discipline: the constitution forbids a separate object store; PostgreSQL BYTEA is the system of record and is sufficient at personal-corpus scale.
- **Auto-promote into concepts / agent-written semantic edges.** Rejected: it crosses the curator-driven-synthesis line the v0.4 plan deliberately left undrawn.

## 5. Open questions (resolve at propose time)

- **Versioning:** last-write-wins only, or keep an append-only history per key (mirroring wiki-page revisions)? Agents often want both a mutable current state and an append log.
- **Binary vs text:** ship text/JSON only first, or BYTEA for arbitrary blobs from day one?
- **Size:** soft guidance vs a hard per-object cap; what `body` size is reasonable in PostgreSQL before it is abuse.
- **GC / TTL:** do objects expire, or is deletion always explicit?
- **Promote dedup:** should promote reuse the existing idempotent-ingest dedup, and what happens on re-promote of a changed object?
- **`object_list` bodies:** metadata-only by default with an opt-in to include bodies?
- **`collection` now or later:** keep the column dormant, or expose it in the verbs from the start as harmless grouping?

## 6. Smoke test sketch (for the eventual Phase Plan)

- `object_put` then `object_get` round-trips the body byte-for-byte (text and, if in scope, binary).
- `object_list` shows the key; `object_delete` removes it; `object_get` then reports not-found.
- An un-promoted object never appears in `query` or `ask` results (retrieval stays page-only).
- `object_promote` makes the object a `source` page that `query` then returns, with provenance back to the object id.
- Promote creates no `concept` page and no semantic edge.
- A wire-format snapshot per new verb (REST == MCP == CLI `--format json`).

## 7. Estimated shape

One migration, one repository module over `psycopg`, five facade verbs plus serialization, the REST and MCP adapters, the CLI verbs, and the tests above. No new store, no new dependency, no new daemon. Fits the one-to-two-weekend phase budget. When promoted to an active phase it follows the standard loop: branch, OpenSpec change, Phase Plan, draft PR, review gate, sub-phase commits.
